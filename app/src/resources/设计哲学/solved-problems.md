# 解决的问题

AgentGo 的建设重点不是让模型在单次对话中“看起来更聪明”，而是把模型、工具、状态、策略和运行环境组织成一个可理解、可控制、可扩展的智能体系统。

本文从需求分析的角度说明 AgentGo 为什么存在、需要解决哪些问题，以及这些问题如何共同指向系统的长期演进方向。

## 一、系统的总体目标

AgentGo 的总体目标是为智能体应用提供一套稳定的运行基础，使开发者能够用清晰的工程方式构建、运行、观察和扩展智能体。

| 目标方向 | 要回答的核心问题           | AgentGo 的基本思路                                     | 预期结果                         |
| -------- | -------------------------- | ------------------------------------------------------ | -------------------------------- |
| 可理解   | 智能体为什么做出这个动作？ | 将观察、思考、决策、执行和反馈组织成清晰的 Agent Loop  | 行为过程可以被解释和复盘         |
| 可控制   | 如何限制智能体的行为边界？ | 将模型、工具、权限、状态和策略纳入统一运行时           | 系统能够控制风险和资源消耗       |
| 可观测   | 系统当前运行到哪一步？     | 显式记录事件、输入、输出、状态和错误                   | 问题可以定位，质量可以评估       |
| 可恢复   | 某一步失败后如何继续？     | 将失败、重试、暂停、回滚和人工介入作为运行流程的一部分 | 长任务不会因为单点失败而完全中断 |
| 可演进   | 如何从原型逐步成长为产品？ | 通过稳定边界承载模型、工具、存储和扩展                 | 系统可以渐进式增加能力           |
| 可复用   | 一套能力如何服务多个场景？ | 抽象通用的循环、上下文、工具和扩展接口                 | 业务场景之间可以共享基础能力     |

从结果上看，AgentGo 要解决的是“智能体应用难以工程化”的根本问题：让一次性的模型调用，逐步变成可以长期运行和持续改进的系统。

## 二、系统要解决的问题

### 1. 用户需求

这里的“用户”包括直接使用智能体完成任务的人，也包括负责设计、部署和维护智能体的开发者与团队。

| 用户需求           | 具体表现                                             | 缺少该能力时的问题                             | 系统需要提供的支持                     |
| ------------------ | ---------------------------------------------------- | ---------------------------------------------- | -------------------------------------- |
| 用自然语言完成任务 | 用户希望用目标和约束描述问题，而不是学习复杂操作流程 | 使用门槛高，智能体只能覆盖固定流程             | 支持自然语言目标、上下文和约束输入     |
| 获得连续的任务处理 | 用户希望系统能够持续执行多步骤任务                   | 用户必须频繁确认和手动衔接步骤                 | 支持多轮循环、任务状态和阶段性反馈     |
| 了解任务进度       | 用户需要知道系统正在做什么、已经完成什么             | 用户无法判断系统是否卡住或偏离目标             | 提供进度、事件、阶段和结果展示         |
| 获得可信结果       | 用户关心结果是否满足目标、是否有依据、是否可复核     | 模型输出可能正确但无法验证，也可能遗漏关键步骤 | 支持结果说明、过程记录、证据和评估     |
| 在失败时继续工作   | 网络、工具、权限或模型调用都可能临时失败             | 一次失败导致整个任务丢失                       | 支持重试、恢复、暂停和人工介入         |
| 控制风险和权限     | 用户不希望智能体任意访问数据或执行高风险动作         | 误操作、越权访问和不可逆修改难以避免           | 支持工具授权、操作确认、资源限制和审计 |
| 适配不同工作方式   | 不同用户、团队和业务有不同的流程与偏好               | 系统只能提供单一固定的交互模式                 | 支持可配置的策略、工具、提示和运行环境 |

这些需求共同指向一个核心结论：用户需要的不是一次更长的回答，而是一个能够围绕目标持续工作的协作系统。

### 2. 系统自身能力

系统自身能力关注 AgentGo 作为运行平台必须具备的基础能力。它们不直接等同于某个具体业务功能，而是支撑所有智能体场景的共同底座。

| 能力领域   | 需要解决的问题                           | 核心能力                                 | 设计关注点                             |
| ---------- | ---------------------------------------- | ---------------------------------------- | -------------------------------------- |
| Agent Loop | 单次调用无法支撑观察、决策和执行的循环   | 统一编排输入、推理、工具调用、结果和反馈 | 循环边界清晰，状态变化可追踪           |
| 上下文管理 | 多轮任务中的信息容易丢失、污染或无限增长 | 管理会话上下文、任务上下文和外部上下文   | 上下文来源明确，长度和优先级可控制     |
| 工具执行   | 工具调用分散在业务代码中，难以复用和审计 | 统一注册、发现、调用、返回和错误处理     | 参数校验、权限隔离和结果结构化         |
| 状态管理   | 长任务需要保存中间结果和当前进度         | 管理短期状态、持久状态和任务快照         | 状态可恢复，变化可观察，数据边界清楚   |
| 策略控制   | 不同任务需要不同的决策、重试和终止规则   | 支持策略注入、阶段控制和退出条件         | 策略可配置、可测试、可替换             |
| 运行环境   | 智能体需要访问外部服务、文件或计算资源   | 提供受控的执行环境和资源边界             | 安全、隔离、超时和资源消耗可控         |
| 可观测性   | 黑盒运行导致问题难以定位和复现           | 记录事件、日志、指标、轨迹和错误         | 观测信息与业务数据分离，便于检索和分析 |
| 可靠性     | 模型和外部依赖具有不确定性               | 支持超时、重试、降级、恢复和人工接管     | 失败是可预期状态，而不是异常终点       |
| 评估与反馈 | 没有评价标准就无法判断系统是否变好       | 支持过程评估、结果评估和人工反馈         | 评估结果能够反向改进策略和配置         |

AgentGo 的系统能力最终要形成一个闭环：

| 输入                     | 运行                                          | 输出                         | 反馈                                   |
| ------------------------ | --------------------------------------------- | ---------------------------- | -------------------------------------- |
| 目标、上下文、约束和资源 | Agent Loop 驱动模型、工具、状态和策略协同工作 | 行动结果、过程记录和任务状态 | 用户评价、系统指标、错误信息和评估结果 |

这个闭环使系统能够从“完成一次任务”进一步走向“持续提升完成任务的能力”。

### 3. 扩展能力

智能体应用的场景差异很大。系统如果只支持一种模型、一类工具或一种部署方式，就无法覆盖真实业务。因此，AgentGo 需要把变化频繁的部分放在清晰的扩展边界之外。

| 扩展对象 | 为什么需要扩展                                   | 典型扩展内容                                   | 需要保持稳定的边界                   |
| -------- | ------------------------------------------------ | ---------------------------------------------- | ------------------------------------ |
| 模型     | 不同任务对成本、速度、上下文和推理能力的要求不同 | 模型提供商、模型路由、结构化输出和流式响应     | 统一的模型调用与结果协议             |
| 工具     | 不同业务需要访问不同的服务和资源                 | 搜索、数据库、文件、浏览器、代码执行和内部 API | 统一的工具描述、参数、权限和返回协议 |
| 存储     | 不同场景需要不同的数据保留和检索方式             | 会话存储、任务存储、向量检索和缓存             | 统一的状态读写与生命周期接口         |
| 策略     | 不同任务的决策流程和安全规则不同                 | 提示策略、路由策略、重试策略和终止条件         | 统一的策略注入和执行上下文           |
| 记忆     | 智能体需要在多个任务之间保留有价值的信息         | 用户偏好、领域知识、任务历史和长期记忆         | 记忆的来源、权限、有效期和可删除性   |
| 交互界面 | 用户可能通过不同终端使用智能体                   | Web、命令行、API、消息平台和嵌入式界面         | 统一的任务、事件和结果模型           |
| 运行时   | 不同部署环境对隔离、性能和资源有不同要求         | 本地、服务器、容器和云端运行时                 | 统一的生命周期、配置和观测机制       |
| 领域模块 | 业务需要复用领域知识和操作流程                   | 客服、研发、数据分析和自动化模块               | 模块可以独立开发、测试和升级         |

扩展能力不是简单地增加插件数量，而是让系统在扩展后仍然保持可理解、可控制和可观测。每个扩展都应明确以下信息：

| 约束问题       | 需要说明的内容                         |
| -------------- | -------------------------------------- |
| 它能做什么？   | 能力范围、输入、输出和适用场景         |
| 它不能做什么？ | 禁止操作、权限边界和资源限制           |
| 它如何失败？   | 错误类型、超时行为、重试条件和降级方式 |
| 它如何被观察？ | 日志、事件、指标和审计信息             |
| 它如何被替换？ | 接口契约、版本兼容和迁移方式           |

## 三、系统未来的展望

AgentGo 的未来不是单纯堆叠更多模型或工具，而是持续提高智能体系统的工程成熟度。

| 发展方向         | 未来需要回答的问题                       | 可能的演进                                   |
| ---------------- | ---------------------------------------- | -------------------------------------------- |
| 更强的任务自治   | 系统能否在更少人工干预下完成复杂任务？   | 更可靠的规划、分阶段执行、动态调整和人工接管 |
| 更高的结果可信度 | 系统如何证明结果可靠，而不是只给出答案？ | 证据链、可复现轨迹、自动校验和多层评估       |
| 更细的安全控制   | 系统如何在拥有行动能力的同时保持可控？   | 最小权限、风险分级、策略审计和可逆操作       |
| 更好的协作能力   | 多个智能体或人机之间如何协同？           | 角色分工、任务委派、共享状态和冲突处理       |
| 更低的使用成本   | 如何在效果、速度和成本之间取得平衡？     | 模型路由、缓存、资源调度和运行时优化         |
| 更开放的生态     | 外部开发者如何安全地贡献能力？           | 标准扩展协议、组件市场、版本管理和兼容性机制 |
| 更完整的评估体系 | 如何持续判断系统是否真的变好？           | 场景基准、线上指标、回放测试和反馈闭环       |
| 更广泛的落地     | 如何让智能体进入真实业务流程？           | 连接企业系统、遵循治理要求并适应组织流程     |

从长期看，AgentGo 希望形成一种新的系统建设方式：

| 当前形态                 | 未来形态                                   |
| ------------------------ | ------------------------------------------ |
| 依赖 Prompt 的一次性应用 | 具备明确边界和生命周期的智能体系统         |
| 依赖人工串联的工具脚本   | 能够自主编排且可审计的任务流程             |
| 难以复现的黑盒行为       | 可观测、可回放、可评估的运行轨迹           |
| 针对单一场景的定制代码   | 可通过模型、工具、策略和模块持续扩展的平台 |

AgentGo 最终要建立的，不只是一个“能调用模型”的框架，而是一套能够让智能体长期运行、持续学习、稳定交付并接受工程治理的基础设施。
